# The demos, as they ran

Records of the programs under [demos/](../../../demos/README.md), rerun for 1.0.0 on 2026-09-23 on one AMD Ryzen 7 7800X3D (8 cores, 16 threads) under WSL2 with clang 21.1.8. Other agents were building and testing on the machine throughout.

| File | What it holds |
|---|---|
| `numeric_host.json` | `demos/numeric/run.py --rounds 7` at `e31fd75`: the plate's 200 sweeps of 1024 x 1024 cells on 16 lanes and on one, beside the C++ loop on 16 OpenMP threads with and without guards and on one thread with them, every run's time and the load average before and after. |
| `implement.json` | `make demo-implement` with the demo as committed: the packet, every submission with the host's full answer, the search without and with the history with every round's times, the difference report, the load average around the timed search, and the run of the program with the chosen selection. |

At `e31fd75` the repair and visual demos printed what their READMEs show, and the visual demo drew frames byte for byte equal to the PNGs in `demos/visual/frames`. The replay of the recorded live run, `demos/repair/live-sonnet-5.json`, gave the answers its README describes. Those two demos time nothing.

The numeric run found every program printing the same fingerprint, so all five computed the same bits, and the CAIRN plate within 0.0000148 of the f64 reference against a contract of 0.0048. Those two results are exact and do not depend on load. The times do. The one-minute load average was 1.1 before the run and 2.2 after, on 16 threads. The medians were 74 ms on 16 lanes, 226 ms on one lane and 210 ms for the guarded C++ loop on one thread. The OpenMP builds took 237 ms guarded and 254 ms unguarded, with runs from 126 ms to 661 ms. This record does not say why the OpenMP runs were slower and more spread than the lane pool, and it is not a comparison of CAIRN with OpenMP; no ratio from it should be quoted.

The implement run validated `sumsq_by4` and the four instances of `sumsq_blocks` on 129 cases each, and refused the two submissions the README shows. The one-minute load average was 7.0 when the timed search started and 6.9 when it ended. The search started 11 runs in 13.8 s within its budget of 16, and chose `plan sumsq use sumsq_blocks[4];`. At n = 65536 the first round, the median of 3 blocks each, measured the reference at 44.1 us and the five implementations at 11.5 to 25.9 us; `sumsq_blocks[4]` then measured 13.0 and 12.8 us, and `sumsq_blocks[8]` 12.2 and 13.2 us. The fastest implementations took about a quarter of the reference's time on this host at this size, and `sumsq_blocks[32]` about 60 percent. The difference between the best two is within the spread of these runs, and an earlier run of the demo chose `sumsq_blocks[8]`. The model predicted the reference fastest and got 3 of the 15 measured pairs in order.

The device half of the numeric demo has not run: it runs only under `make gpu`, which writes `results/demos/numeric/device.json`. Its build compiled for sm_120 in `tests/projects/test_demos.py`. The repair demo's one live run, claude-sonnet-5 through `claude -p`, is `demos/repair/live-sonnet-5.json` beside the demo, with its date and cost; no model was asked again for this release.
