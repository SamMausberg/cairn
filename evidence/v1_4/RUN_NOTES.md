# CAIRN 1.4 run notes

Taken on the machine of the 1.3 record: an AMD Ryzen 7 7800X3D (eight cores, sixteen lanes) under WSL2 on Linux 6.18, g++ 13.3.0, clang++ 21.1.8, CUDA 13.2 with an NVIDIA GeForce RTX 5070 Ti, libz3, oneTBB, Lean 4.34.0 through elan. 2026-09-22. `summary.json` is `tools/release/collect_evidence.py --release v1_4` on the committed tree at `ca709c8` (not dirty): every gate passed, and the suite ran 3,758 tests with 46 skipped. `lean/` is `tools/release/collect_lean_evidence.py --release v1_4` at the same commit; it records the tree as dirty only because `summary.json` had just been written beside it. The Lean build succeeded from scratch over 91 audited declarations, which use `propext` and `Quot.sound` and nothing else. `bench/` is the preregistered suite, run at `a090489` with no agent of this repository running. Every other record under this directory was taken while the 1.4 work landed, on a machine shared with other agents' builds and suites, and says so in its own notes.

## What 1.4 added, and how each was checked here

- The short forms: bare variants, one-statement arms, compound assignment, call statements, element loops, `lends`, `_`, test blocks with `assert` and `assert_eq`, and `print`, `println` and `format`. Each has a rejection table naming its codes, native runs under both compilers with the sanitizer that bites, and a sweep of the library, the examples and the docs whose emitted C++ was compared before and after with `tools/checks/emission_identity.py`. No program emits a guard more.
- Justified guard elision. Each removed guard carries the facts that justify it and `verify/elision.py` checks each proof before a line is emitted; `guards/` compares the optimized and the conservative build on 174,816 generated cases per compiler with no difference, and Lean proves the part rule (`lean/facts_differential.json`).
- The numerics. Every pattern of `f16`, `bf16`, `f8e4m3` and `f8e5m2` against an exact rational model, `quantize` at its boundaries, `derive grad` against central differences and torch, and the classifier example trained and run quantized.
- `scan`, fusion, device plans and the tensor-core multiply. The pooled and fused forms agree bit for bit with the forms they stand for under both compilers and ThreadSanitizer (`scan/`, `fusion/`); device plans and `mma_unordered` compile for sm_120, and a host simulation of every device thread's steps caught every fault planted in the tiling. None of the device paths ran on the device.
- The library: `std.fmt`, `std.fs`, `std.env`, `std.time`, `std.math`, `std.zlib`, `std.image` and `std.draw`, each against an independent oracle (Python's formatting, `zlib` and `Counter`, a Python rasterizer), and the I/O ring's recoverable answers under fault injection.
- The tools: `cairn predict` (validated in `perf_model/`), `cairn tune`, `cairn diff` (run on the release in `diff/`), `cairn shot`, `cairn state`, `cairn migrate`, the C header and the ctypes binding, the templates, the language server's project-wide rename, and the terminal output.
- Two adversarial reviews (`review/`) found nine defects, all in tools and none a soundness hole in the language, each fixed with its regression test.

## Performance records

`bench/` finds the lane pool level with OpenMP and oneTBB at equal guards, as in 1.3, and closes two of 1.3's three losses: the parallel host `reduce` and the lane-owned-block histogram are level with the privatized baselines and beat the sequential loop by the preregistered margin. `dot_f64` keeps its written order and still loses to a reassociating reduction, by design. `runtime/` measures reused task threads against a thread per task, `fusion/` and `scan/` measure what they added, and `perf_model/` records how `cairn predict` did against timings calibration never saw: a median error of 28 to 44 percent and a Kendall tau of 0.87 to 0.92, with the ranges it gets wrong named. The pool's on-demand claims lose cache affinity under load between a hundred thousand and ten million elements, where oneTBB's static partition does not; that is a finding for the runtime, not yet addressed.

## What was not done

No code ran on the GPU. Everything 1.4 added for the device (vector loads, shared staging, device plans, `mma_unordered`, the device scan, the execution context) is compiled for sm_120 and checked on the host only, and the device half of `cairn predict` is NVIDIA's published specification with four assumed values. `make gpu`, `make calibrate-device` and `make tune-device` are the owner's to run, and until they do, no device claim is made. The execution context is not wired into the emitted code. The freestanding target did not run: `qemu-system-aarch64` and an AArch64 host are absent here. The VS Code extension was not packaged, because `vsce` is absent and nothing is downloaded. The preregistered edit-protocol trial did not run, since it needs fresh model subjects, and no comparative AI experiment ran; the context numbers in `context/` are scripted transcripts. The SMT model answers `unknown` for storage floats, quantizing, asserts and `scan`, and the elision audit's rules are hand-written, not proved in Lean. The records are from one machine.
