# Verification

Nothing proves the whole compiler correct. Three mechanisms each establish something narrower: Lean 4 proofs about hand-written models, Z3 queries about a modeled fragment of the source, and executed tests. A result from one says nothing about what the others cover. Accepted, typed, native-built, finite-tested, sanitizer-clean, SMT-equivalent, Lean-checked and benchmarked are separate claims, and `unknown` is none of them.

## The Lean project

`proofs/` is a dependency-free Lean 4 project. The toolchain is pinned in `proofs/lean-toolchain`, Mathlib is not used, and `lake build` checks it from scratch in a few seconds. There is no `sorry`, no `native_decide` and no added axiom: every audited declaration depends on `propext` and `Quot.sound` at most, and `Classical.choice` appears nowhere.

The certificate module is generated from the Python rules; `tools/checks/export_lean_certificates.py --check` fails if the two drift, and the compiler receipt reports `lean_verified: true` only while the live bundle hashes to the bundle Lean checked. ## The collector certificates and the loop model

`compact` lowers to a loop whose one store carries no dynamic bounds check:

```c
k = 0;
for (i = 0; i < n; ++i) { if (pred(i)) { out[k] = proj(i); ++k; } }
used = k;
```

`out` has capacity exactly `n`, and `pred` and `proj` never read `out`. What licenses the unchecked store is the cursor invariant `0 <= k <= i <= n <= M`, where k is emitted outputs, i visited inputs, n capacity and M the largest representable cursor. While `i < n`, the store at k is in range and both increments fit. Emit substitutes `k'=k+1` and `i'=i+1`, skip substitutes `k'=k` and `i'=i+1`, initialization substitutes `i=k=0`, and on exit `k<=n`.

`src/cairn/verify/linear_certificates.py` writes an affine form as five exact integer coefficients over `(1,k,i,n,M)`, read as "this form is nonnegative". A rule fixes premises a_j and a conclusion g. Its certificate gives nonnegative integer multipliers c_j and a nonnegative integer c_0, and the checker accepts only when, coefficient by coefficient, `g = c_0 + sum_j c_j * a_j`. Under any assignment satisfying a_j>=0 every summand is nonnegative, so g>=0. The argument is universal over integer assignments, not an enumeration of states. The store bound is the identity `n-k-1 = (i-k) + (n-i-1)`; the emitted-cursor bound adds `M-n`.

Seventeen obligations cover initialization, nonnegative and in-range stores, both increments, emit and skip preservation, and output-count boundedness. Some initialization obligations are trivial identities; seventeen is an obligation count, not seventeen independent theorems. The compiler checks the fixed bundle before every emission, mutation tests confirm that a corrupted bundle blocks compilation, and there is no user-editable assumption channel. The receipt pins the rules and the checker source by SHA-256.

Lean adds three results. `Cairn.check_sound`: if the checker accepts a rule, the rule's conclusion is nonnegative for every integer assignment that satisfies its assumptions.

```lean
theorem Cairn.check_sound {r : Rule} {c : Certificate} (h : check r c = true) :
    ∀ K I N M : Int, (∀ a ∈ r.assumptions, 0 ≤ a.eval K I N M) →
      0 ≤ r.conclusion.eval K I N M
```

`Cairn.Collector.all_checked`: all seventeen certificates pass that checker inside Lean, by `decide` (the kernel replays the exact integer arithmetic), and each named obligation becomes a Lean theorem by applying its certificate. `Inv K I N M` bundles `0 ≤ K`, `K ≤ I`, `I ≤ N`, `N ≤ M`, and each transition theorem is proved by applying the corresponding certified obligation, not by re-deriving the arithmetic:

```lean
theorem Inv.init {N M : Int} (hn : 0 ≤ N) (hm : N ≤ M) : Inv 0 0 N M   -- initial.*
theorem Inv.emit  (h : Inv K I N M) (hlt : I < N) : Inv (K + 1) (I + 1) N M -- emit.invariant.0-3
theorem Inv.skip  (h : Inv K I N M) (hlt : I < N) : Inv K (I + 1) N M      -- skip.invariant.0-3
theorem Inv.store_nonneg         (h : Inv K I N M) (hlt : I < N) : 0 ≤ K   -- store.nonnegative
theorem Inv.store_lt_capacity    (h : Inv K I N M) (hlt : I < N) : K < N   -- store.strictly_below_capacity
theorem Inv.emit_increment_fits  (h : Inv K I N M) (hlt : I < N) : K + 1 ≤ M -- emit.cursor_increment_fits
theorem Inv.step_increment_fits  (h : Inv K I N M) (hlt : I < N) : I + 1 ≤ M -- step.input_increment_fits
theorem Inv.exit_le_capacity     (h : Inv K I N M) : K ≤ N                 -- exit.output_count_bounded
```

And for an executable model of the loop, where `State β` carries `(out : List β, k : Nat, i : Nat)`, `step` performs `out[k] = proj x; ++k` on a selected input and always `++i`, and `collect` starts both cursors at zero: the invariant is preserved by every iteration (`run_preserves_inv`), every store is in bounds with no dynamic guard, both increments stay representable, and the result is stable selection.

```lean
theorem store_index_lt_capacity (pred : α → Bool) (proj : α → β)
    (xs : List α) (out : List β) (hcap : out.length = xs.length)
    (pre : List α) (x : α) (post : List α) (hsplit : xs = pre ++ x :: post) :
    (run pred proj pre ⟨out, 0, 0⟩).k < out.length

theorem increments_fit (pred : α → Bool) (proj : α → β)
    (xs : List α) (out : List β) (hcap : out.length = xs.length)
    (M : Int) (hM : (out.length : Int) ≤ M)
    (pre : List α) (x : α) (post : List α) (hsplit : xs = pre ++ x :: post) :
    ((run pred proj pre ⟨out, 0, 0⟩).k : Int) + 1 ≤ M
    ∧ ((run pred proj pre ⟨out, 0, 0⟩).i : Int) + 1 ≤ M

theorem collect_spec (pred : α → Bool) (proj : α → β) (xs : List α) (out : List β)
    (hcap : out.length = xs.length) :
    (collect pred proj xs out).k = (xs.filter pred).length
    ∧ (collect pred proj xs out).k ≤ out.length
    ∧ (collect pred proj xs out).i = xs.length
    ∧ (collect pred proj xs out).out.length = out.length
    ∧ (collect pred proj xs out).out.take (collect pred proj xs out).k
        = (xs.filter pred).map proj
    ∧ (collect pred proj xs out).out.drop (collect pred proj xs out).k
        = out.drop (collect pred proj xs out).k
```

The prefix `out[0..k)` is exactly `(inputs.filter pred).map proj` in input order, `k` is the number of selected inputs and is within capacity, the buffer does not change length, and the tail `out[k..n)` is untouched. `store_index_lt_buffer_length` states the store bound against the live buffer at the moment of the store, so `List.set`, which is total and would silently discard an out-of-range write, never discards anything.

Trusted here: Python's exact integer arithmetic, the small checker's implementation, and the connection between the compiler's cursor operations and these transitions, which rests on code review. The certificates say nothing about alias or lifetime safety, memory initialization, compiler bugs or native machine behaviour, and they license only this one store. Every other guard the compiler leaves out rests on the guard-elision rule below.

## Ownership and leases: a mechanized core calculus

`Cairn/Places.lean` and `Cairn/Ownership/` are a second, independent development: a small ownership-and-lease calculus with an executable checker, an interleaving small-step machine with explicit error states, and checked safety and progress theorems. It is written by hand beside `src/cairn/compiler/checking.py`, so it shows that the rules are safe as a set. Whether `checking.py` follows them is what the differential harness tests.

### Locals and places

A local is the unit of ownership: it is allocated, moved, dropped and released. A place is what one borrow names, with one constructor per shape `checking.py:path` produces and one per case `checking.py:lend` chooses between.

| Lean | source | what it is |
| --- | --- | --- |
| `whole x` | `d` | the owner itself, header and elements: what an `rw<Buf[T]>` parameter lends, and the only borrow through which a task can replace the cell (`swap`) |
| `hdr x` | the `len(d)` read | the header alone: the length and the identity of the cell (`leased(..., elements=False)`) |
| `elems x` | `d[]` | every element: what an array view `rw<T>[n]` of a whole owner lends |
| `part x lo hi` | `d[lo..hi]` | those elements |

Each place carries a root: a local plus a field path, which is what `path` writes as `r.a.b`. `r.xs[lo..hi]`, `r.xs[]` and `len(r.xs)` are the same four shapes at the root `r.xs`. A bound is an integer literal or the name of an immutable natural. The names are read by an arbitrary valuation, and every theorem quantifies over every valuation, so no result depends on the numbers.

Anything else `path` writes as `?`, and the three shapes that produces are conservatively modelled as `elems`. A single element `a[i]` is `"a[]"` whatever the index is. A part of a part `a[lo..hi][j..k]` is `"a[?..?]"`. A part one of whose bounds can change, `a[m..3]` for a mutable `m`, is `"a[?..3]"`. Each of them overlaps every place of its base, contributes no `lo <= hi` fact to the chain, and still leaves a `len` read alone, and `elems` does exactly those three: `ovl elems part` and `ovl elems whole` are `true`, `Place.range (elems r)` is `none`, and `ovl hdr elems` is `false`. The case table is beside `Place` in `Places.lean`, its rows are pinned as `example`s under `ovl`, and the classifications agree with `checking.py` on the programs in the regression, each run through `python bin/cairn check` and pinned in `tests/soundness/test_soundness.py`. Those are named programs; nothing proves the mapping for every program.

### Disjointness, decided twice

The checker decides overlap syntactically, as `checking.py:overlaps` does. Places of different locals never overlap. The header and the elements do not overlap, which is why `len(d)` stays readable while a view of `d`'s elements is lent, and does not while `d` itself is lent. Two roots meet exactly when they are the same local and one field path is a prefix of the other, so distinct fields of one record are apart and a field and its record are not. Two parts of one root are disjoint exactly when one visibly ends at or before the other begins. Everything else overlaps, and `whole x` overlaps every place of `x`.

"Visibly ends at or before" is `reaches`: the same bound, a literal comparison, or a chain through the `lo <= hi` facts of the parts in play. That is the reflexive-transitive closure `checking.py` searches depth-first, saturated one round at a time here. The machine decides overlap under the valuation: two accesses collide when both touch the header or their index ranges meet. `Ownership.ovl_sound` is the bridge between the two.

The two Python rules use different fact sets, and the model keeps them apart. `leased` chains through every part the live tasks hold, plus the place being touched. `disjoint` chains through the parts of the one argument list it is looking at. So handing a single call `d[0..a]` and `d[b..n]` is rejected even while `d[a..b]` is lent to a live task, because that argument list contains nothing to order `a` before `b`, while spawning the same two ends one at a time is accepted. Both checkers behave that way, which can refuse a safe program and never accepts an unsafe one.

### The guard, and the trap

A slice is formed by `cr::part(p, lo, hi, n, want)`, which traps unless `lo <= hi`. Only `lo <= hi` matters to the alias rules, so only it is modelled. The machine performs that guard for every part a statement names, on the spawner's thread, before the call is made or the task is started. A failed guard is a trap: a fourth configuration beside running, finished and faulted, and a defined abort of the whole configuration, live tasks included, which counts as neither a fault nor a race. The invariant `TasksGuarded` states that every part a live task holds was guarded, and `inPlay_guarded` adds the place being touched. That is what makes `d[6..3]` safe to accept: that slice orders `d[0..6]` before `d[3..9]`, which overlap, and the program aborts at its spawn before either task exists (`tests/soundness/test_soundness.py::test_a_backwards_part_used_to_order_two_others_aborts_at_its_spawn`).

### Syntax, checker and machine

A program is one scope: a list of declared locals plus a body. Statements are `alloc x` (a fresh heap cell lands in `x`), `mkScalar x` (a copyable scalar), `copy y x`, `move y x`, `drop x` (the implicit release at the exit of an inner scope), `call args` where `args` is a list of `(place, ro|rw)` borrows lent for the duration of the call, `spawn t args` (the borrows stay lent until `wait t`), `wait t`, `ite thn els` with both branches, `parallel i in n { body }`, and the task-group statements `group g n`, `submit g args` and `collect g`. A read of a scalar is `call [(whole x, ro)]`, a write of a part is `call [(part x lo hi, rw)]`, and `let k = len(x);` is `call [(hdr x, ro)]`. Borrows are second class by construction, since a borrow exists only as an entry in one argument list.

`Ownership.accepts` is an executable Lean function whose decisions can be evaluated. It carries the state `checking.py` carries in its `Scope`: which locals hold a scalar, which hold an owner, which are dead, which groups are live, and a lease map from a ticket or a group to the borrows it holds. It enforces: only declared locals; no use of a dead local; `copy` only of a scalar; no move, drop or rebinding of a local any of whose places is leased; no read of what a live task writes and no write of what a live task reads or writes; no two overlapping borrows with an `rw` among the arguments of one call; a fresh ticket per `spawn` and a fresh name per group; no submission to or collect from a group that is not live; at a branch join, a local moved on one path is dead afterwards, both branches must agree on which tickets and groups are live, and a group holds what either path lent it; and no live ticket or group where the scope ends.

The machine is a small-step semantics over a heap of allocation ids, a liveness map and a per-cell release counter. It is deliberately undefensive, so that the faults are reachable for programs the checker rejects: `copy` duplicates whatever bits a local holds, which is how a mis-accepted copy of an owner reaches a double free, binding a local releases what it held before, and a move leaves a ghost mark whose only purpose is to let a later use be named `UseAfterMove`. The error configurations are `UseAfterMove`, `UseAfterFree`, `DoubleFree`, `Leak` (a live ticket or group where the scope ends), `Race`, `AliasedArgs` and `DeadGroup` (a submission to or a collect from a group after its `wait`); `Trap` is not one of them.

Concurrency is interleaving. A task's body is abstracted to its footprint: while its ticket is live it may touch any place it was lent, in the mode it was lent, between any two steps of the spawner, any number of times. A task holding the whole owner `rw` may also replace the cell, which is what `swap` through a lent owner does; one holding only elements or a part cannot. `Race` is reached when the spawner and a live task, or two live tasks, touch a common location of one local with a write among them. `if` has an opaque condition, so both branches are always reachable and the join is what makes a one-sided move dead.

### Parallel regions

`parallel i in n { body }` is a statement whose body is a list of lane accesses, which is what `checking.py:region` keeps in `Lanes.accesses`: for each place of the enclosing scope the body touches, its root, the stride of the lane's own block the access is shown to stay inside, and whether it writes. Five shapes are modelled: `x[i]` at the lane's own index; `x[i * S + j]` or any access the facts place in the lane's own block `[i * S, i * S + S)`; `x[e]` for any other index expression, and any part or view lent on to a call that nothing places, whose footprint is every element; the place itself (a shared scalar read or assigned, or a single borrow lent on); and `len(x)`.

The rule is `checking.py`'s: whatever any lane writes may be touched only inside the lane's own block, with one stride for every access to that local, keyed on the root local, and a `len` read is not recorded at all. The element rule is the block of stride 1. Assigning a shared scalar is `E-PARALLEL-WRITE` there; here it fails the same rule. Every lane access is checked against the leases of the enclosing scope under the place `where` writes, so a region beside a task holding any part of the same array is rejected, conservatively, as `checking.py` rejects it. A body is a list of accesses, so a region cannot nest, `return`, move an outer owner or run a collector.

`lanesOf n body` builds one thread per index below `n`, holding `part x [k * S, k * S + S)` where the body names the block of stride `S` and the worst case elsewhere. Lanes have the same shape as tasks and step by the same rule, so `stepThread` serves both, and the invariant's clauses about live threads range over `tasks ++ lanes` together: one `Pairwise` says no two threads conflict, whether two tasks, a task and a lane, or two lanes. The spawner is blocked while a region runs, which is what "completes before the next statement" means; `Region.lean` proves that the pool keeps that promise. Race freedom between two lanes is `meets_own_block`: what any lane writes, every lane touches only inside its own block of one stride, and blocks of one stride for two indices are apart.

### Task groups

A group is a name that many tasks share. `group g n` declares it with room for `n` tasks, `submit g args` starts a task under the name `g` exactly as `spawn` does, and `wait g` removes every task of that name and the group itself, which is what `wait(g)` does in `checking.py` and at run time. `collect g` joins one finished task. Which one is not known, so the machine has one successor per task of `g` that might have finished, and the checker keeps every lease: the checker's leases may name more than the machine's live tasks, never less. A submission to a full group and a collect from a group with nothing outstanding are traps, as `cr::par::Group` makes them.

The branch join is where groups differ from tickets. Both paths start from one state, and a group may be lent different places on each. After the join the group holds what either path lent it, and a part keeps its bounds only if both paths lent it, since its `lo <= hi` guard ran only where it was formed. This is `checking.py:settle`, and before 1.4 both it and the loop rule were missing: `tests/soundness/test_groups.py::test_what_a_group_holds_survives_every_path` has the four programs that raced. The witnesses `groupLeaseFromOnePath_races` and `groupFactFromOnePath_races` below are the two branch cases in the machine.

A join now claims more than either path, so the code after an `if` is accepted from a state weaker than the one the machine is in. `Le c' c` says `c'` claims no more than `c`: fewer live locals, the same groups, and every lease of `c` held through a lease of `c'` under the same name, where a lease may name the elements in place of a part (`Within`). `Checks` is acceptance that may forget between two statements, `joinOf_le` shows the join claims no more than either path, and `Sync.weaken` shows that forgetting keeps the invariant. Preservation is an induction over `Checks`.

### The lane pool

The calculus blocks the spawner while lanes run. `Cairn/Region.lean` proves that the lane pool behind `cr::par::run` does that. A wide region is a counter lanes claim chunks from. The thread that starts the region loads the counter and, while it is below `n`, bumps it by the claim size and runs the indices it claimed; it unlinks the region when it finds nothing left and returns once no worker is inside. A pool worker joins only a linked region with work left, claims chunks the same way, and leaves when it finds none. Every step is atomic in the model: a load, a bump, running one chunk, a join, a leave, the unlink and the return.

Under every interleaving of any number of workers, with any claim size, `runs_once` says that when the starter returns every index below `n` has run exactly once and nothing at or past `n` has run, and `quiet_when_back` says that no worker is inside. `finishes` says that from every state a region reaches, with a positive claim size, it returns while only the starter and the workers already inside take steps, so a region never waits for a worker to arrive. The invariant behind them is that every index below the counter has run or is running in exactly one lane, and every index at or past it is untouched.

The model is sequentially consistent. The C++ bumps the counter with a relaxed `fetch_add`, which only hands out indices, and orders a leaving worker against the waiting starter with the sequentially consistent operations `leave` and `settle` pair. That the header performs these steps is review. A region below `lanes::CUTOFF`, or in a process with one lane, is the plain loop on the thread that starts it.

### The theorems

Every statement below is proved in `proofs/Cairn/`, audited in `Cairn/Audit.lean` and required by `tests/verification/test_lean_proofs.py`. `Reach ρ p.scope (Cfg.start p) cfg` means "`cfg` is reachable from the initial configuration of `p` under the interleaving semantics, when the immutable bounds are worth what `ρ` says". The valuation is universally quantified: an accepted program is safe for every one.

```lean
theorem reaches_sound {ρ : Valuation} {facts : List Fact} (hf : FactsTrue ρ facts)
    {x goal : Bound} (h : reaches facts x goal = true) : x.eval ρ ≤ goal.eval ρ

theorem ovl_sound {ρ : Valuation} {inPlay : List Place}
    (hg : ∀ p ∈ inPlay, p.guard ρ = true) {r s : Place}
    (h : ovl inPlay r s = false) : meets ρ r s = false

theorem accepted_no_fault {p : Program} (hp : accepts p = true) {ρ : Valuation} {cfg : Cfg}
    (hr : Reach ρ p.scope (Cfg.start p) cfg) (e : Err) : cfg ≠ Cfg.err e

theorem accepted_threads_disjoint {p : Program} (hp : accepts p = true) {ρ : Valuation}
    {code : List Stmt} {tasks lanes : List Task} {st : State}
    (hr : Reach ρ p.scope (Cfg.start p) (.run code tasks lanes st)) :
    (tasks ++ lanes).Pairwise (NoRacePair ρ)

theorem lanesOf_pairwise (ρ : Valuation) : ∀ (n : Nat) {body : List Touch},
    laneRule body = true → (lanesOf n body).Pairwise (NoRacePair ρ)

theorem accepted_frees_each_allocation_once {p : Program} (hp : accepts p = true)
    {ρ : Valuation} {st : State} (hr : Reach ρ p.scope (Cfg.start p) (Cfg.done st)) :
    (∀ a, st.live a = false) ∧ (∀ a, a < st.next → st.frees a = 1)

def Progress : Prop :=
  ∀ (p : Program) (ρ : Valuation), accepts p = true →
    ∀ cfg, Reach ρ p.scope (Cfg.start p) cfg →
      (∃ st, cfg = Cfg.done st) ∨ cfg = Cfg.trap ∨ succ ρ p.scope cfg ≠ []

theorem accepted_progress : Progress
```

`accepted_no_use_after_move`, `accepted_no_use_after_free`, `accepted_no_double_free`, `accepted_race_free`, `accepted_no_leaked_ticket`, `accepted_no_use_after_wait` and `accepted_no_aliased_args` are `accepted_no_fault` at each named error. The race theorem covers the whole calculus. It rests on `Ok_succ`, the preservation lemma: every successor of a configuration satisfying the invariant satisfies it too, the invariant is `False` on error configurations, and it is trivially true of a trap. The release theorem is about normal termination only; a run that traps has aborted, and nothing is claimed about the cells it leaves behind. `accepted_progress` is cheap on its own, because the machine is total by construction; its content is that the stuck configurations are exactly the errors, which `accepted_no_fault` excludes.

The safety theorems would be vacuous if the machine could never fault, so a fault is also shown reachable for programs the checker rejects, each by exhibiting the step sequence. `leasedRead_races`, `overlappingTasks_races`, `overlappingParts_races`, `sameFieldToTwoTasks_races`, `laneWritesFixedIndex_races`, `laneWritesShared_races`, `laneReadsOther_races` and `laneTwoStrides_races` drive the machine to `Race`; `fieldPartsOverlapInOneCall_aliases` to `AliasedArgs`; `copyAnOwner_doubleFrees` to `DoubleFree`; `useAfterDrop_usesDeadPlace` to `UseAfterMove`; and `unawaitedTicket_leaks` and `groupNeverWaited_leaks` to `Leak`; `collectAfterWait_deadGroup` to `DeadGroup`; and `groupLeaseFromOnePath_races` and `groupFactFromOnePath_races` to `Race` after a join. `witnesses_are_rejected` and `group_witnesses_are_rejected` confirm that the checker rejects all sixteen. Each witness is one `decide` over a bounded search of the machine's successors, turned back into a `Reach` derivation by `found_reach`. `UseAfterFree` is the one error configuration with no witness. `backwardsPart_traps` is the other side: that program is accepted, and under the valuation it is written for the machine reaches `Trap` at the guard of `d[6..3]` before any race.

### The differential harness

`tools/checks/differential_ownership.py` is the one mechanical link between the two checkers. A seeded generator emits programs in the fragment both understand and renders each one twice from a single intermediate: as CAIRN source, and as a Lean `Program` literal. `compile_program` classifies the source, one `lake env lean` run over one generated file evaluates `accepts` on every literal, and the two verdicts must match for every program. A disagreement prints both renderings and fails; a diagnostic outside the ownership set the calculus models fails too, since that means the generator left the fragment.

The fragment is a table in the harness, and `--fragment` prints it. In: `alloc`, `mkScalar`, `copy`, `move`, `call`, `spawn`, `wait`, `if`, `parallel i in n { ... }` with the five lane access shapes, blocks of stride 2 and 4 and the element one past a block among them, task groups with submissions and collects on any path and `wait(g)` on one path, both or after the branches, and the places `whole`, `hdr`, `elems` and `part` over plain locals, with bounds drawn from the literals `0`, `2`, `4`, `8` and the immutable `a`, `b`, `n`. Out by construction: record fields, `drop`, a lane that calls anything, `lane:f`, a nested region and a region inside a branch, device work ordered by `after`, closures, placement, `reduce`, `compact`, `take`, `swap`, loops, traits, generics, re-binding a local, a ticket spawned inside a branch, a group declared inside a branch or a loop, a group or ticket passed to a callee (`E-PINNED`), and a branch-local name used after the branch. The generated programs are checked, never built or run.

Two renderings are not one program, and three places state that. `elems` is written in CAIRN as `f(len(d), d)`, so the CAIRN side charges a header read the Lean side is given as its own `call [(hdr d, ro)]` in front of the call. A branch is a scope in CAIRN and not in the Lean model, which is why a name a branch declares is never used after it. And a lane body is rendered as one statement per access, so that the statements a lane runs and the `Touch` list the model carries are the same list in the same order.

```sh
python tools/checks/differential_ownership.py --count 2000 --seed 7
CAIRN_DIFFERENTIAL_N=5000 python -m pytest -q tests/verification/test_differential_ownership.py
```

`make test` runs 40 programs and `make lean` runs 200. The test also plants one wrong verdict and requires the harness to report it, because a comparison that cannot fail is not evidence. Without `lake` the test skips with the reason and the harness exits 3 rather than passing.

## The guard-elision rule

Lowering leaves a guard out where `compiler/facts.py` shows it cannot fail, and `proofs/Cairn/Facts.lean` proves the rule it uses. A fact is `x - y <= k` between two atoms: zero, an immutable `usize` value, or one times a positive stride. `distance` finds the least `k` the facts give by Bellman-Ford, over the facts, their copies scaled by every stride in play, and the two things every atom satisfies: a value is at most the largest usize and at least zero. `bounds` gives the terms an expression is known not to exceed and to reach, and four decisions read them: an index below its extent, a `+` at most the largest usize, a `-` whose right side is at most its left, and a value at most a constant, which covers a shift count and a narrowing conversion.

`distance_sound` says the search returns a true bound under every valuation that makes the facts true. `bounds_sound` says every bound holds of the value of an expression that evaluates without a trap, with checked `+`, `-` and `*`, and `/` and `%` that trap on zero. `index_sound`, `add_sound`, `sub_sound` and `atMostConst_sound` are the four decisions. The Lean functions are transliterations of the Python ones, down to the order in which bounds are kept and the four `WIDEST` of them, and `tools/checks/differential_facts.py` asks the real Python functions and the Lean ones the same generated questions and requires the same five answers. Twenty thousand inputs agreed on the run recorded in `evidence/v1_4/lean/facts_differential.json`, and planting an off-by-one in `index`, or a sum bounded by one side alone, is reported within a few hundred.

What stays tested: that the facts in scope are true wherever they are visible. A loop, lane or collector binder brings its bounds, a `let` what bounds its initializer, a condition, the left side of `&&` or `||` and an early exit what they say, and every fact names only values that cannot change while it is in scope. That bookkeeping is `tests/soundness/test_established.py`, which also checks generated programs against an evaluator of its own under AddressSanitizer. The model has no `usize(x)` of a narrower integer, and the lane blocks `window` places are the ownership calculus's `Touch.block`, not this file's.

## Value-level source equivalence

`src/cairn/verify/scalar_semantics.py` and its companions evaluate a fragment of the source symbolically, and Z3 answers whether two versions of one function can differ. The model has exact-width integer and Boolean values, `f32`/`f64`, records, tag-only enums and payload sums with `match` and `try`, array views and the parts `x[lo..hi]` taken from them, single borrows of values, fixed local storage (`stack x:T[N] = zeroed;` and `Array[T, N]` locals), function-local heap owners (`buffer x:T[n] = zeroed;`, `Buf[T](n)`), `compact`, host `reduce`, checked and wrapping operations, explicit conversions, assignment to a name, a field or an element, branching, short-circuiting, bounded `for` and `while` with `break` and `continue`, early return, `void` results and acyclic calls.

An observation is the returned value, the length and the elements of an owner that is returned, and the final contents of every `rw` parameter, or one undifferentiated abort. An owner inside a record, a sum or an array, recursion, tasks, lanes, device placement, closures, `dyn` dispatch, atomics and the foreign boundary are unsupported: each returns unknown with the reason that refused it.

Views. A view parameter is one SMT array per scalar component of its element, read and written at `offset + i` while `i` is below the extent its signature names. The extent is a literal or an earlier `usize` parameter, so `xs` and `out` of `fn f(n:usize, xs:ro<T>[n], out:rw<T>[n])` share one extent term. `len(xs)` is that extent, an index at or above it is the trap `cr::at` takes, and a part shifts the window under the one guard `cr::part` applies. The admitted inputs are the ones the emitted entry guards admit: `cr::view` says each view is a valid, aligned region of its extent, and `cr::disjoint` says the storage behind an `rw` view is distinct from every other view of the same call, so two `rw` views are independent arrays. Read-only views may alias. Independent arrays with equal contents include that case, so the query ranges over at least every input a caller can build. An `rw` view is observed element by element over its whole extent. A part is a window into the storage it was taken from, so two views of one array in one call share one array term: a write through either lands in the base and the caller sees it afterwards. The callee's `cr::disjoint` guard is modeled as the emitter runs it, so an `rw` window that meets another window of the same storage aborts, which `E-ALIAS` keeps an accepted program from reaching, and read-only views of one array may alias freely.

Owners. A local owner (`buffer` scratch or `Buf[T](n)`) is zeroed storage with a length of its own. `take(x)` moves that storage into the result and leaves storage of length 0 behind, so `len(x)` answers 0 and an index of `x` traps, as a moved-from `cr::Buf` does; `swap(a, b)` exchanges the two storages and their lengths; assigning over an owner replaces its storage. A `Buf[T]` parameter passed by value is storage of any length and any contents, because no entry guard reads an owner, and a precondition bounds its `len` as it bounds an extent. A `Buf[T]` that is returned is observed by its length and its elements, element by element like an `rw` view, and one returned by a callee flows to the caller as storage. An owner held inside a record, a sum or an array is not modeled and is named as the reason.

Tags. A value is flattened into its scalar components: a record is its fields in declaration order, a sum is the emitted `std::uint32_t` tag beside every variant payload, an inline array is its elements. Two values look alike when their components do, except that a sum compares its tag and the payload of the active variant only. Quantification admits what the emitted entry guard admits: `if (tag >= n) cr::trap();` reads the top-level tag of a value parameter whose type is an enum or sum, and nothing else, so that tag names a declared variant while a tag nested inside a record field, an array element or a payload, and every tag in storage behind a view, carries any value. A `match` over a tag that names no variant leaves no surviving path, so the call aborts, and a `try` over one is unknown; the abort assumes that `codegen.py` closes every emitted `switch` with `default: cr::trap();`; `tests/verification/test_semantics.py` compares the two sides on such a tag rather than deriving the trap from the C++. A record or sum named in the signature must have the same definition on both sides, or the answer is `invalid-contract`.

Collectors and reductions. `compact` is unrolled as the host emits it: the predicate once per input, the projection only where it selects, the store at the running count, the tail untouched, and the count returned. `reduce` is the in-order host fold from the identity the emitter uses, offered for `add_wrap`, `mul_wrap`, `&`, `|`, `^`, `min`, `max` and the checked unsigned `+`. `reduce ... parallel` is the same fold, because its blocks give the in-order answer for every operator it admits. A float reduction, whose order is unspecified, is unknown.

Traps. Checked `+ - *`, division and remainder by zero or signed-minimum over minus one, narrowing and sign-changing conversions, shift counts at or above the width, the array bounds guard and the float-to-integer guard all abort. Every abort is one observation, so "both trap" counts as equal behaviour. By default the reference must additionally return on every admitted input, and `allow_reference_traps` is the explicit opt-out.

Floating point. `f32` and `f64` use Z3's FloatingPoint theory. Every operation rounds to nearest even exactly once, which is the contract the compiler builds with. Comparisons are the IEEE predicates, so a `NaN` operand compares false and `+0.0 == -0.0`, while equality of results is equality of the IEEE datum, so returning `-0.0` is not the same function as returning `+0.0`. `cr::truncate` is modeled as the header writes it, so NaN and out-of-range values trap. Two assumptions are stated rather than proved: that the C++ compiler rounds a decimal literal to nearest even, and that the host evaluates `float` arithmetic in `float`. The theory has exactly one NaN and cannot speak about payload bits, so if an observed float may be NaN on an admitted input, the answer is `unknown`, never `smt-equivalent`; a caller who does not care excludes them with a precondition (`assume="x==x"`).

Loops. `for`, `while`, `compact` and `reduce` are unrolled up to 16 iterations, and what would still be running after that becomes an obligation of its own: Z3 is asked whether any admitted input reaches a seventeenth iteration, and anything but "no" is `unknown`. Mutually exclusive paths are merged at the end of each iteration, so a branching body costs iterations rather than powers of two. An extent is symbolic, so a pass over `0..n` is unknown until a precondition bounds `n`; a literal extent needs none. A timeout is `unknown`.

Evaluation order. Traps are order-insensitive, because one abort is the same observation wherever it happens. A `try` is not, so it is modeled only as the whole right-hand side of a binding, an assignment, a return or an expression statement, and a `try` written as an operand of a larger expression is unknown.

The query. The fixed host-owned reference R, candidate C and domain D produce definedness/value pairs (d_R,v_R), (d_C,v_C). The checker requires a well-defined nonempty domain, a complete unrolling, and by default a reference that returns on all admitted inputs, and asks Z3 whether `D && ((d_R != d_C) || (d_R && d_C && v_R != v_C))` is satisfiable. Unsatisfiable, with no reachable NaN in what is observed, means `smt-equivalent` in the named source model. A satisfiable counterexample is replayed through an operational evaluator over Python values before it is reported; storage a counterexample lends is read back by naming the first 16 elements of every view, and a mismatch that needs a longer view is unknown. A missing tool, a translation error, unsupported syntax, an exhausted budget, a replay that disagrees and a solver timeout are all `unknown`. The receipt records the source and translator identities, the query hashes, the solver version and every outcome. No proof is reconstructed in Lean, and no theorem relates this translator to native output. A reference that states the wrong requirement is checked as faithfully as a right one.

## Whole-module coverage

`cairn verify --all` parses and checks both complete sources, compares public records, enums and sums, and enumerates every function on both sides. Missing or extra entries, unsupported functions, mismatched types, partial references or any undecided obligation prevent `smt-module-equivalent`. Each entry keeps its own result, the receipt lists covered and uncovered functions, and one uncovered function keeps the whole module incomplete.

`--assume` supplies a precondition per function, and repeats:

```sh
python3 bin/cairn verify reference.cairn candidate.cairn --all --assume 'total=n<=4'
```

A restricted entry is equivalent only where its precondition holds, so the receipt keeps every text under `preconditions`, each entry keeps its own `assume`, and the module's `domain` names them. A precondition that names no declared function is refused, one that admits no input is `invalid-domain`, and a function with none is compared over the whole domain. There is a 64000-byte limit per input, at most 128 functions, and a soft 30-second solver budget, which is not a sandbox. `examples/proof_scope/mixed.cairn` is the negative fixture: comparison with itself must remain incomplete, because it contains a function that moves an owner. Empty coverage is incomplete, and a change to a public type blocks the module result even when every function agrees.

## Tests, native code and failures

Accepted programs run natively under both compilers and under AddressSanitizer, UndefinedBehaviorSanitizer, LeakSanitizer and ThreadSanitizer. Device guards are exercised by death tests that must abort the host. A sanitizer-clean run shows the absence of those faults on the inputs it ran. Generic code is checked per instance, so a template nothing instantiates is unchecked, and the receipt lists it.

The 1.0 rules as `checking.py` implements them are outside the calculus: affine and linear values, second-class borrows, leases over parts whose bounds are not visible, the effect rules a lane's callees obey, placement and the effect fixed point. Acceptance and rejection tests exercise them, and nothing connects them mechanically to the calculus. The instrumented lifetime counters run at O0, so they say nothing about allocation counts in an optimized build. `testing.evaluate` requires a passing behavioural report and a successful child exit, so a process that prints a pass and then crashes has failed. Equal native sections show identical code under one compiler and one set of flags, and nothing about correctness or speed.
