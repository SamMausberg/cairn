# Typed assembly and foreign implementations

Taken on 2026-09-23 on one AMD Ryzen 7 7800X3D under WSL2 (Linux 6.18), with g++ 13.3, clang++ 21.1.8 and CUDA 13.2's nvcc and cuobjdump. Other agents were building and testing on the machine throughout; nothing here is a timing. `python3 evidence/v1_0/foreign/collect.py` writes the four records again. No GPU ran anything: device code was compiled for sm_120 and read with cuobjdump, and no binary that launches a kernel was executed.

## What ran

`assembly.json`: the x86-64 program of `tests/language/test_assembly.py`, ten typed statements (an output that starts at an input, register clobbers, a read and a write through an array's address, SSE operands, an 8-bit register, the `%k` modifier, a fence, a volatile `rdtsc`), built by g++ and by clang++ under the address and undefined sanitizers and run. Both printed exactly the values Python computes from the instructions' definitions, and neither sanitizer reported anything. The PTX program of the same file compiled for sm_120, and its SASS holds the instructions the statements name: `BREV` for `brev.b32`, `LDG.E.CONSTANT` for `ld.global.nc.u32`, `MEMBAR.ALL.GPU` for `fence.acq_rel.gpu`.

`host.json`: `vendor/histogram.cpp` of `examples/foreign/host`, a C++ histogram written for this example with four interleaved tables, as a foreign implementation of the CAIRN `histogram_u32`. The program builds with it under both compilers, and `cairn validate`'s 256 boundary cases, each call in a process of its own with the vendored object linked, agreed with the reference under clang++ and under g++: finite-tested on those cases. `tests/projects/test_foreign.py` also runs both functions on every length below 70 under the address and undefined sanitizers with both compilers, and shows that dropping the C++'s tail loop fails on a case whose length is not a multiple of four.

`device.json` and `inspection.json`: `examples/foreign/device`, with `vendor/stencil.cu`, a shared-memory tiled 3-point stencil written for this example, as a foreign implementation of `stencil_1d` (the blend of `bench/suite/kernels/stencil_1d`, with its views on the device), and `vendor/parallel_gpu.cu`, a byte-for-byte copy of `bench/gpu/parallel_gpu.cu`. The program, the stencil and the benchmark all compiled for sm_120 with the project's flags, `-Werror all-warnings` included; the benchmark was compiled and not linked, since the program calls nothing in it. ptxas reports the tiled kernel at 11 registers, 1,032 bytes of shared memory and no spills, and nine kernels in the benchmark: its three lane kernels, CUB's scan and reductions, and CUB's empty kernel. Validation's twelve device tests for the stencil were generated and built.

## What did not run

The stencil kernel has not run on a GPU, so it is not finite-tested: its record says `not-run`, and `make gpu` runs `test_the_device_implementation_runs_against_its_reference_on_the_gpu`, which no one has run. The typed PTX has not run on a GPU either; it compiles for sm_120, and its instructions are in the SASS. AArch64 typed assembly is checked and lowered but has not been built, since there is no AArch64 host here. Every foreign contract is declared and trusted: nothing checks that the C++ or the CUDA does only what its extern says, and finite tests are not a proof that it computes the reference for every input. The SMT comparison `cairn validate` attempts is `unknown` for a foreign implementation, since the solver cannot see its body.
