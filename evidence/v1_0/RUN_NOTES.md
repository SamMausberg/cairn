# CAIRN 1.0 run notes

Everything here was executed on one rented host on 18 September 2026: an NVIDIA GH200 (Grace, 64 AArch64 cores, H100-class GPU, 97 GiB device memory), Ubuntu 22.04, kernel 6.8, Python 3.13.15 (the suite was also run under 3.11, the declared floor), clang++ 15.0.7, g++ 11.4 and 12.3, CUDA 12.8 (nvcc 12.8.93, driver 580.105), Z3 4.8.12, Lean 4.34.0, qemu-system-aarch64. No x86-64 host was available, so the x86-64 profile is exercised only by the toolchain table and its tests, not by a native run. Nothing was uploaded and no remote workflow ran.

`summary.json` is written by `tools/collect_evidence.py` on a committed tree: formatter, linter, type checker, `cairn fmt --check`, the whole test suite, the certificate gate, the Lean export drift check and scalar module equivalence. A gate whose tool is missing is recorded as unavailable, never as passed. `lean/`, `gpu/` and `embedded/` hold the three hardware- or tool-specific records, each written by the harness that produced it.

## What the suite executes

- Every accepted 1.0 construct natively under clang++ and g++; the ownership program under Address, Leak and UndefinedBehavior sanitizers; the task program under ThreadSanitizer; owned dynamic values under AddressSanitizer.
- The runtime headers' own self-checking binaries, including death tests: a guard that fires inside a CUDA lane must abort the host, an unawaited ticket or task must trap. One launch covers 4,294,967,299 lanes.
- CAIRN programs on the GPU: lanes, `kernel fn` helpers, lane-local storage and sums in lanes, device `reduce`, device stream compaction and transfers, with host expectations.
- The freestanding AArch64 image under QEMU with an exact UART transcript and exit status, and a second image whose bounds guard must trap (status 134).
- The standard library (ten modules) and four applications written in CAIRN: a checksummed log-structured store with crash replay and compaction, a TCP line-protocol service exercised over a real socket, a Jacobi simulator whose sequential, host-parallel and device back ends agree bit for bit, and a GPU pipeline checked element-wise against the host.
- The formatter over every `.cairn` file plus randomized whitespace and comment fuzz; a real `cairn lsp` subprocess; the canonical projection round-tripping every sample and `std` module to identical native code; edit sessions refusing races, shared writes, allocations and undisclosed callees past their ceiling.
- A from-scratch `lake build` of `proofs/` with an axiom audit (only `propext` and `Quot.sound`).

## Audits

Three review passes changed the compiler. An adversarial audit of the new checker produced fourteen accepted-but-unsound programs, each confirmed by a sanitizer, a wrong effect row or a build failure; all are fixed and pinned in `tests/test_soundness.py`. A second adversarial round (one lead reviewer on ownership, leases, lanes and the device, one on generics, traits and modules, one on the emitter; all read-only, working from pinned snapshots while fixes landed) reported some forty further findings, among them a use after free through a closure, data races through closures and dynamic references in lanes, writes through `ro<dyn>`, a linear value leaked through a self-owning record, a heap overflow from two locals that differed only by an underscore, and the discovery that `src/cairn/std/core.cairn` had never been committed because `.gitignore` matched `core.*`. A third reviewer then attacked only the rules those fixes introduced and reported nine more, one of them unsound (a host view dereferenced on the device through a helper function; it ran here only because a GH200 makes host pages device-addressable). Each was reproduced here before it was fixed, each fix carries a rejection or native behavior test, and the suite was then run from a pristine `git archive` of the branch, where only the history audit (which needs `.git`) does not apply. The first real user of the language (the agent that wrote `std` and the applications) reported seven compiler bugs, pinned in `tests/test_language.py`, and a list of ergonomic gaps, of which checked float-to-integer conversion, `try` across sum families, `extern "symbol"`, receiver-first method lookup, multi-trait bounds, `kernel fn`, expression extents for parts and dead-function elimination were implemented. An audit finding that was reported but could not be demonstrated on this host (operand-order dependence between clang++ and g++ on AArch64, both of which evaluate left to right) was fixed from the rule rather than from an observed divergence.

## What was not done

No whole-compiler, ownership-calculus or native-refinement proof. No run on an x86-64 host, no second GPU, no multi-device work. The GPU and host-parallel benchmark is one machine and three kernels; its own notes record that host regions lose below roughly ten million cheap elements and that the device's end-to-end advantage on this machine leans on NVLink-C2C transfer rates. `bench/codegen_only.py` finds five of nine selected function sections byte-identical to the C++ references on AArch64 (the 0.6 figure of eight of nine was x86-64 with another compiler). No model was trained or evaluated: the edit protocol, packets and rule cards cover the language, but no fresh-model experiment ran, and token counts remain byte counts.
