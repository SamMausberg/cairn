# The first device session on a GH200

The suite's device tests ran on a GH200 on 28 September 2026, through two runs of `make gpu`'s test half. It was the first device run on a Hopper GPU since the 0.8.0 to 0.8.2 records, and so the first there for every device feature added after 0.8.3. The first, at `dda8208`, failed three tests, and each failure was a defect: a miscompiled kernel, a test built for the wrong GPU, and a Compute Sanitizer result read wrongly. The second, at `449189b`, `main` after the five fixes this session made, passed every test it ran. Nothing was timed.

## The machine

An NVIDIA GH200 480GB: a Grace CPU (Neoverse-V2, 64 cores visible to Linux) running Ubuntu 22.04.5 with Linux 6.8.0-1046-nvidia-64k, and a Hopper GPU of compute capability 9.0 with 97,871 MiB of memory. The GPU drives no display (`display_active` is Disabled) and was in persistence mode under driver 580.105.08. CUDA 13.0 (`nvcc` V13.0.88) was first on `PATH`, with Compute Sanitizer 2025.3.1, and nvcc's host compiler was the machine's g++ 11.4 or clang++ 14, as each test names one. Every test resolved the device target `sm_90`, which `nvidia-smi` reports for this GPU. Other agents' builds and test suites shared the CPU during both runs, and every device run held `/tmp/cairn-gpu.lock`.

## What ran

1. `make gpu`'s test half at `dda8208` (`main` after #141): `CAIRN_GPU_TESTS=1 python -m pytest -q -p no:xdist --device-runs` over the Makefile's `GPU_TESTS`, which collected 52 tests. 46 passed, 3 failed and 3 skipped, in 3 min 30 s. `make_gpu_dda8208.txt` is its output.
2. Narrow device runs to find each failure's cause, each through the lock: builds of `tile64`'s test program with Compute Sanitizer's memcheck, with guards that recorded their operands before trapping, and with the candidate fix; the device validation tests one at a time under initcheck and memcheck and without a tool; and each fixed test once on its branch. One debugging build of `tile64`, whose bounds check printed instead of trapping, ran until its 600 s timeout, for the reason given below.
3. `make gpu`'s test half at `449189b`, from 17:35:24 to 17:38:57 UTC: the same command, with `-rA` added so that pytest names each result. It collected the same 52 tests. 49 passed and 3 skipped, in 3 min 32 s. `make_gpu.txt` is its output, and `make_gpu_tests.txt` lists each test with its result.
4. One narrow run of `verify/validation/device.py`'s `sanitized` over the device validation tests' own program at `449189b`, to record each Compute Sanitizer tool's result, which the test checks without printing: `sanitizers.json`.

The skipped tests are the three that trap on the device on purpose, which run only with `CAIRN_GPU_TRAPS=1`, left unset: a layout coordinate out of range in a lane, `test_gpu_runtime_device_traps`, and a checked device total that overflows. `make gpu`'s second command, `bench/gpu/parallel_gpu.py`, did not run.

## The three failures

`tests/soundness/test_tensor_kernels.py::test_each_kernel_keeps_the_contract_on_the_device[tile64]` stopped with `cairn: cuda: unspecified launch failure`. Compute Sanitizer placed the traps in the kernel's first loop, and the recording build showed `c[37]` read with `cn = 1` by a thread whose row lies past `m`, where the source's `if` keeps that read from happening. CUDA 13.0 compiles every target below sm_100 with NVVM 7.0.1, and NVVM 7.0.1 had deleted the loop's normal exit: the PTX for sm_90 ended in that loop, with no WMMA instruction after it, so the loop ran on until a guard trapped. `tests/runtime/test_device_arithmetic.py` keeps the loop reduced to eight lines: counted loops whose checked arithmetic can leave through a trap the compiler knows does not return. The same kernel compiled by NVVM 20 for sm_120 is whole, which is why it passed on the RTX 5070 Ti in the 1.1.0 session. The debugging build that printed instead of trapping had no way out of the loop, and hung.

#164 makes the device trap below sm_100 an asm that the compiler must assume returns, and lowers a `match` so that no path leaves its `switch` after a trap. With it, `tile64` and `tile32` kept `mma_unordered`'s contract on this GPU. CUDA 13.0 compiles the broken `tile64` for sm_75 through sm_90a alike, so the defect was not particular to this GPU.

`tests/projects/test_foreign.py::test_the_device_implementation_runs_against_its_reference_on_the_gpu` failed 11 of its 12 generated tests with `cairn: cuda: no kernel image is available for execution on the device`. `examples/foreign/device` pins `device_target = "sm_120"`, whose code has no image a 9.0 device can load; the one test that passed launches nothing. #166 builds that test for the GPU it runs on, and makes a test block stopped by such a CUDA error give that error as its reason, where the record had said "a guard failed".

`tests/verification/test_device_validation.py::test_each_sanitizer_tool_is_a_result_of_its_own_on_the_device` found every tool `reported`. Two of the eight generated tests have empty views and make no CUDA call, so each tool printed `Error: Target application terminated before first instrumented API call` and exited 255, which the validator read as a finding. The other six exited 0 under every tool. #165 runs a test that made no CUDA call once more without the tool and counts it by how it ends there. It does not pass `--require-cuda-init no`, with which a program that exited 2 before its first CUDA call made the tool exit 0.

## What passed

The 49 tests of the second run each ran device code on this GPU and checked its result against the host, a reference or a plain loop. They cover the modules `GPU_TESTS` names at `449189b`: device regions with and without plans, `vector` and `stage` plans, wide loads and stores, atomic updates, cooperative regions with a finish, votes and shared arrays nobody zeroes, pipeline stages, the device `scan` and `compact`, `reduce op out[k]`, typed PTX, the execution context and `cq_` entries replayed in a CUDA graph, the finish counter, the tensor-core multiply on f16, bf16, f8e4m3 and f8e5m2 inputs, the `tile64` and `tile32` kernels, `examples/apps`' device applications, the heat plate of `demos/numeric`, and the foreign CUDA kernel of `examples/foreign/device`.

Under Compute Sanitizer, memcheck, racecheck, initcheck and synccheck each reported no error for the six device validation tests that did device work, and each tool's result was `clean` (`sanitizers.json`). That is one small program, a scaling of a device view by a region and its two-region implementation, run on the inputs its boundaries generate. No other device test ran under Compute Sanitizer.

The same commit holds two more fixes made in this session for failures of the fast suite on this machine, which ran no device code: #169, which gives `cairn predict` and `cairn tune` the device target of the card that prices them instead of the GPU present, and #168, which keeps a counterexample Z3 found when a narrowing query runs out of time.

## What the run does not show

It does not show a guard failing in a device lane on purpose: the three tests that do so did not run. The broken `tile64` build did trap in a lane, and the process stopped with the message the runtime documents, but that is one unplanned case. Nothing was timed, so the cost of #164's trap for code below sm_100, which leaves more trap sites in the PTX, is not known. Each test ran once, on one GPU, under CUDA 13.0 alone; the NVVM 7.0.1 finding was compiled, not run, under CUDA 12.8, and CUDA 12.9 and 13.2 were not tried here. The Hopper features that nothing lowers yet (`wgmma`, TMA, clusters) did not run. `docs/verification.md`'s capability matrix and the documents that name the RTX 5070 Ti as the one GPU a feature ran on are not changed by this record.
