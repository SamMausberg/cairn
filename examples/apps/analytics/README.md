# analytics — a columnar engine whose table types are generated

A million wire-encoded trades on disk, read back into a structure of arrays, filtered,
aggregated and grouped four different ways. Nothing here is a table type the compiler knows
about: `Trade_table`, `Trade_get`, `Trade_summarize`, `Trade_unrolled_price` and the rest are
generated by three recipes in `src/cols.cairn`, which are ordinary CAIRN and derived twice over
— once for a record of this module, once for a record of another one.

Every query is answered twice, and `main` returns 0 only if the two answers agree: row-wise
against column-wise, the contracted collector against the loop, a sequential pass against host
lanes, one pass against four tasks, a bound against a table lookup. The device configuration
adds host against device.

## What it demonstrates

* **Recipes as the schema layer.** `columns/1` generates the table record (one `Buf` per field
  plus the row count), the row accessors, a row digest folded over the fields with `fold ^`, and
  the static facts `bytes(R)` and `count(R)`. `stats/1` generates a summary record and four
  functions per column (min, max, a checked total and a wrapping one). `unrolled[K]/1` takes a
  natural and generates a K-accumulator kernel per column — `derive cols.unrolled[4] for Trade;`
  and `derive cols.unrolled[8] for sensor.Reading;` differ only in that number.
  `device_columns/1` generates the same reductions over `@device` views. Between them they use
  `each` at declaration, statement, field-list and call-argument level, `where` values,
  `require` with a domain message, `$` splices in names and types, and a recipe reaching its own
  module's public helper by its full path (`cols.chain`).
* **Generated code is ordinary code.** The generated names belong to the module that wrote the
  `derive`, so the rest of the program says `schema.Trade_summarize(...)`; they carry effect
  rows (`Trade_total_qty` traps, `Trade_key` is `pure`); and one of the two records derived in
  `analytics.schema` is declared in `analytics.sensor`.
* **Two totals, because they are two different claims.** `reduce +` over an unsigned column
  traps if the total does not fit, in any association order; `reduce add_wrap` is exact under
  any association and is therefore the one the device tree reduction is compared against. The
  program computes both and insists they agree on this dataset.
* **A K-way task split.** `venue_sums_tasks` lends four visibly disjoint row ranges and four
  disjoint blocks of one scratch buffer to four tasks at once, waits for all four and merges.
  Overlap the blocks by one element and the checker says `E-LEASED` at the second `spawn`.
* **Lanes that call the caller's closure.** `map_par[T, U]` is generic, its lanes call `f`, and
  its row carries `lane:f`; whatever is passed is judged where it is written, so
  `|x:u64| -> u64 { return mul_wrap(x, factor); }` is fine and a closure that assigned `factor`
  would be `E-PARALLEL-CALL`.
* **Pluggable aggregators both ways.** `run_static[A: Aggregator]` is monomorphised per
  aggregator; `run_dyn(a:rw<dyn Aggregator>, ...)` dispatches; `Vec[Dyn[Aggregator]]` is a query
  plan assembled at run time. All three answer the same numbers.
* **Generated comparisons behind hand-written impls.** A recipe holds functions and records
  only, so `columns/1` generates `Trade_same` and `Trade_less` over the schema and
  `analytics.schema` writes the two one-line `impl`s that forward to them. That is what lets
  `sort.sort` order whole rows; `sort.sort_by` takes the closure the query actually wanted
  (descending price) instead.
* **A queued device pipeline.** `spawn transfer`, `spawn parallel ... after up_price, up_qty`
  and `spawn transfer ... after work` put two uploads, a region and a download on streams; the
  host folds its own copy of the same product meanwhile, and the two totals must agree.

## Effect rows worth noticing

```
cols.chain                    (empty)
schema.Trade_key              read:row, trap
schema.Trade_total_qty        read:c, trap                    checked `reduce +`
query.notional_loop           read:price, read:qty, write:out, trap
query.notional_par            read:price, read:qty, write:out, trap, par:host
query.map_par[u64, u64]       ... indirect_call, lane:f, par:host
query.venue_sums_tasks        ... spawn, join, alloc, free
agg.run_static[SumAgg]        read:a, read:xs, write:a, trap
agg.run_dyn                   read:a, read:xs, write:a, trap, dispatch
gpu.queued_notional           ... spawn, join, par:device, transfer:h2d, transfer:d2h, gpu_alloc
```

The two derived-column functions differ in exactly one effect, and the generator's helper
`chain` has an empty row, so a generated digest costs nothing but arithmetic.

## What the timings say

Ingest dominates: 24 ms to encode, write, read and decode a million 21-byte rows, against 2 ms
for a full pass over a column. Host lanes do not pay off here — `notional_par` over 10⁶ cheap
elements is no faster than the loop, because every `parallel` statement creates and joins its
threads (the same break-even the simulator app reports). On the device the three queries take
1 ms against 2.3 ms on the host, but the download of the kept prefix costs 2 ms on its own: as
in `gpu_pipeline`, moving the answer is dearer than computing it, which is why the language
makes you write the `transfer`.

## Compiler issues this app works around

* A generic function called with a **part of a record's `Buf` field** (`f(n, c.price[0..n])`
  where `f` is generic) crashes the checker with a Python `IndexError`. The workaround here is
  to pass the whole field with `len(c.price)` as its extent, which is why `map_par` and
  `bins_tally` are called that way in `src/main.cairn`.
* A recipe body holds `each`, `require`, `struct` and `fn` — **not `impl` and not `kernel fn`**
  (both are `E-PARSE: Expected 'fn', found ...`). So a generator cannot give its record a trait,
  which is what the two forwarding impls in `src/schema.cairn` are for, and the device helper
  `gpu.notional_of` is hand-written beside the generated device reductions.
* `@pinned` is not accepted where `@host` is expected, so the queued pipeline copies the columns
  into pinned staging buffers by hand in `src/gpu_main.cairn` rather than lending them.
* `cairn check --generics` certifies `run_static` and rejects the rest: `Bins[T]` needs zeroed
  storage of a `T` and `map_par` reads `src[i]` by value, and no bound can yet say "copyable".
