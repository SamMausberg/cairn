# The performance model, calibrated and checked against measurements it was not fitted to

`cairn predict` prices a program from its checked work and a machine profile, without building or running it. This directory holds the one host profile the package ships, how it was measured, and how well its predictions matched two sets of measurements that calibration never saw. Every number here is from one machine, and the device side is a published specification that no run has confirmed.

## The profile

`zen4-7800x3d.json` is the profile as `python -m cairn.perf.calibrate --out ...` wrote it on 2026-09-22: an AMD Ryzen 7 7800X3D (eight cores, sixteen lanes, 32 KiB L1d and 1 MiB L2 per core, 96 MiB L3) under WSL2, clang++ 21.1.8, `-march=x86-64-v4` with the build's own flags. Every figure comes from a CAIRN kernel compiled and timed by `cairn.perf.measure`: stream bandwidth at four working-set sizes on one thread and on every lane, the latency of an access whose address comes from data, the cost of starting a host region on two to sixteen lanes, a task start, an allocation, and a shared atomic. The cost of each kind of operation is a non-negative least-squares fit over twenty-four single-purpose kernels, each counted by the same counter the predictions use, built once with the vectorizer and once without. The clock, 4.67 GHz, is llvm-mca's cycle count for a dependent xor-shift-multiply chain divided by its measured time. `--arch x86-64 --into` then measured the same operation kernels for the family baseline, which a project builds for by default, so a default build is priced at its own vector width: there a 64-bit multiply, a double and a compare keep a loop scalar, which on `x86-64-v4` they do not.

The first calibration's allocation was the cost of nothing. Its kernel returned the length of a `Buf` it never read, and clang removed the allocation, as C++ allows, so the profile said 1.61 ns. The kernel now reads back what it allocated, and `--into ... --allocation` measured it again on 2026-09-22: 18 ns to allocate and release one element. At twice glibc's largest dynamic mmap threshold (64 MiB) the allocator maps the buffer afresh on every call, and zeroing it faults each 4 KiB page on its first touch: 2.7 us a page on this WSL2 host, beyond the bandwidth of the zeroing and the read. The model now charges that for every allocation of 32 MiB or more (`page_ns`, `mapped_bytes`). A smaller buffer, allocated and released call after call, comes from memory the allocator kept, so it pays no fault after the first call, and the model does not charge one. Neither change moves a validation point below, because no kernel of the suite allocates in the function that is timed; `evidence/v1_0/fusion/` has the kernels whose predictions it changed.

The machine was shared: five other agents were building and testing on it throughout. Each figure is the least-disturbed of nine blocks, because a busy machine only ever adds time, so a quiet machine may be a little faster. Three calibration runs within an hour measured a task start at 31, 85 and 121 us, which is the size of the noise in the least stable figures. The packaged copy, `src/cairn/perf/profiles/zen4-7800x3d.json`, adds two facts that run computed and did not write, which the second pass below reads: eight physical cores (`cores`), and the working set each level's bandwidth was timed at (`measured_bytes`). Calibration writes both now.

## The validation

`tools/checks/perf_validation.py` predicts every CAIRN arm of the preregistered suite's eight kernels at six sizes and compares with two sets of timings. `validation_v0_8_3_record.json` compares with `evidence/v0_8_3/bench/suite.json`, the suite's recorded first run on this machine, under both compilers. `validation_fresh.json` compares with `fresh_record.json`, the same entry points timed on the same day by `cairn.perf.measure` on the shared machine, clang++ only, including the two 1.4 arms the first run did not have. That record also keeps each point's least-disturbed block, the statistic calibration uses, and the tool scores the model against it too. No kernel of the suite is among the calibration kernels, and nothing below was fitted to either record. Both files hold the model as it is now; the first model's numbers are beside it here and in `structure_2.json`.

|---|---|---|---|---|---|
| v1.3 record, clang++ | 60 | 44% before, 44% now | 41, now 43 | 0.915, now 0.920 | 0.67 to 0.96, now 0.63 to 0.96 |
| v1.3 record, g++ | 60 | 42%, now 40% | 47, now 47 | 0.907, now 0.916 | 0.60 to 0.87, now 0.67 to 0.91 |
| fresh, clang++, medians | 66 | 33%, now 37% | 47, now 48 | 0.857, now 0.871 | 0.31 to 0.88, now 0.40 to 0.92 |
| fresh, clang++, least-disturbed blocks | 66 | 35%, now 28% | 47, now 46 | 0.870, now 0.881 | |

The error depends on the regime, and the table says where to trust the model and where not to.

| regime (clang++) | v1.3 record | fresh, medians | fresh, least-disturbed |
|---|---|---|---|
| up to 1e4 elements, one lane | 23%, now 20%; 16 of 20 within 2x | 20%, now 19%; 18 of 22 | 18%, now 12%; 17 of 22 |
| 1e5 to 1e7 elements, a wide region | 57%, now 52%; 15, now 17 of 30 | 72%, now 68%; 18, now 19 of 33 | 62%, now 65%; 19, now 18 of 33 |
| 1e8 elements, bound by memory | 6%, now 12%; 10 of 10 | 16%, now 21%; 11 of 11 | 12%, now 13%; 11 of 11 |

Small regions, sequential folds and streams too large for the last cache are predicted within tens of percent. A wide host region between a hundred thousand and ten million elements is still the model's weak range: after the second pass the v1.3 record still has such regions up to five times slower than predicted, and the fresh timings of one kernel at one size varied by up to six times from one run to the next as the other agents' load changed. The model says so: every prediction for a wide host region carries `medium` confidence and names this finding. A histogram's bins and anything else addressed by data carry `low`, and the model tells the agent to measure.

The ranking is better than the times. Within one size, a Kendall tau of 0.63 to 0.96 on the v1.3 record means the model orders kernels mostly correctly, which is what a tuner needs from it. The fresh timings at 1e5 and 1e6, the noisiest points, rank worse.

## The second pass: what was wrong, and what changed

The first model priced four things wrong, and its own records showed which. Each change below is structural: it prices a mechanism the evidence exposed, it refits nothing, and a test in `tests/tooling/test_predict.py` pins it on a machine made up for the test. `structure_2.json` holds every number this section cites, before and after, with the timings this pass took. Those timings ran on the shared machine at a load average of 11 to 13 on sixteen threads, so their pattern means more than any one cell.

A wide region does not find its chunks in its own cores' caches. Calibration never timed the first two levels through a region: it set their every-lane bandwidth to one thread's times the eight cores, which assumes each lane rereads what its core cached on the call before. The pool claims chunks on demand, so the chunk a lane gets is usually one another core last touched. The v1.3 record shows the difference: OpenMP and oneTBB, whose static schedules keep a chunk on one core, ran `saxpy_f32` at 1e6 in 25 to 32 us, the old model predicted 28 us, and CAIRN's region took 225 us. A wide region's streams now come from the lane's own cache once in as many cores as it engages, and otherwise from the shared level that holds the whole working set, at the bandwidth calibration timed through a region. That moved `saxpy_f32`, `stencil_1d` and `mixed_u64` at 1e6 from a tenth to an eighth of their measured time to a fifth to a quarter on the v1.3 record, and `saxpy_f32` from 0.39 to 0.74 of the fresh record's least-disturbed block.

A sibling lane adds nothing to a vector loop. `mixed_u64` at 1e6, a chain of vectorized 64-bit multiplies, took 184 to 186 us on eight lanes and 168 to 191 us on sixteen, against about 800 us on one. The two lanes of a core share its vector units, so a vector loop's compute is now shared among physical cores. A scalar loop, a chain and an irregular access leave room a sibling fills, and are still shared among lanes: capping them too made the blocked histogram, a scalar read-modify-write, predict twice its measured time. The profile now records the eight cores.

A fold hides the work beside it. A fold's step waits for the step before it, and an out-of-order core runs the rest of the body in that wait. The fused `energy` chain squares inside an in-order `f64` fold and measured 0.69 ns an element at 1e6, one dependent add at 4.67 GHz; the old model added the squares' cost to the add's and predicted fusion would lose, 0.73x to 0.81x, where it won 1.5x to 2.2x. Compute is now the larger of the chain and the rest. Every calibration kernel has one or the other, so the rule prices each exactly as the fit did. Repriced with it, `evidence/v1_0/fusion/fusion.json` calls no fusion a loss that measured a win, where the old model called four, its median error per time fell from 41% to 27%, and its Kendall tau over the measured speedups rose from 0.69 to 0.74.

The speed of light counted sixteen lanes of compute. It now counts the eight cores that compute, so a vector loop at the machine's peak no longer reads as half of it.

Where it got worse, plainly. Against the fresh record's medians the median error rose from 33% to 37%, though against its least-disturbed blocks, the statistic calibration keeps, it fell from 35% to 28%. At 1e8 the median error rose from 6% to 12% on the v1.3 record: `dot_f64` there moves its stream from memory at nearly the rate its fold runs, the model takes the larger of the two, and the pair overlap less than fully; the old sum happened to land closer. `dot_f64` from 1e6 up is now 15% to 25% below the fresh record's least-disturbed blocks. The pooled scan at 1e5 went from 0.91 to 1.41 of its least-disturbed run (`evidence/v1_0/scan/`), while at 1e6 it went from 0.30 to 0.65. `sum_u64_pool` at 1e6 went from 0.70 to 1.25 of its least-disturbed block.

Still open. Fused `digest` at 1e7 is predicted at 204x where it measured 39x to 62x, and `stencil_1d` at 1e7 at a quarter of its time, for one reason: a wide stream of 80 MiB fits the 96 MiB cache but ran at nearer memory's rate than the cache's, while calibration timed that cache at 32 MiB only. A bandwidth curve over working sets taken in this pass was too disturbed to calibrate from: one thread read 80 MiB at 20 GB/s, where the v1.3 record streamed the same working set at 89. A prediction for a wide region between the working set calibration timed the last cache at and its capacity now says so and carries `medium` confidence. The rest of the weak range is the pool and the machine: in the same v1.3 run, oneTBB matched the prediction at 1e6 where CAIRN's region took several times longer, which is a finding about the lane pool's on-demand claims under load, not a price the model can derive.

## What this does not show

Nothing here is a device measurement. `src/cairn/perf/profiles/rtx-5070-ti.json` is NVIDIA's published figures for the RTX 5070 Ti with four assumed values marked as assumed, and device kernels are read at compile time (ptxas registers and spills, cuobjdump instruction mix) and never run. The device model has no validation: it gains one only from device timings the owner runs. Nothing here compares CAIRN with another language, and one machine is not a population: another host needs its own calibration, and `cairn predict` says when it is using a profile measured somewhere else.
